# Требования к внешней интеграции: партнер интеллектуальных устройств

### Контекст и допущения
PropDevelopment добавляет для собственников два сервиса «Умного дома»: интеллектуальный домофон 
(открытие по лицу) и интеллектуальный шлагбаум (открытие по номеру автомобиля). Распознавание, 
видеообработку и управление устройствами выполняет внешняя платформа партнёра. Со стороны нашей
системы - добавляются новые сервисы `intelligence-devices-events-app` (Kotlin, Spring Boot) и
`intelligence-devices-events-worker` (Java) для асинхронного вычитывания событий из Кафки со своей БД 
`intelligence-devices-db` (PostgreSQL), `intelligence-devices-events-app` доступен из мобильного
приложения «Витрина сервисов для собственников». Новые сервисы делаются исходя из соображений
**анализа производительности**, чтобы в последствии легко можно было замасштабировать это и место
обработки коллбеков не стало боттлнеком из за своей возросшей нагрузки.

**Допущения**:
- Партнёр один, это платформа, которая отвечает как за свои устройства установленные на всех объектах
различных УК так и за работу CV (Computer Vision).
- Решение об открытии из заранее загруженной биометрии/номера машины принимает платформа партнёра
по списку разрешённых лиц и номеров, который мы синхронизируем. Устройства должны работать и при
недоступности наших систем.
- Мы не храним биометрию пользователей, не пишем в логи и тела запросов не трассируем, не отдаём в
брокер и CDC. Изображение в виде байтов проходит через наш новый сервис только в транзите,
фотографии лиц хранятся только у партнёра.
- Интеграция двусторонняя: наши HTTP запросы уходят партнёру, его события приходят нам колбэками
также в виде HTTP запросов.

### 2. Протоколы аутентификации и авторизации
#### 2.1. Аутентификация по каналам
| Канал | Протокол и механизм | Детали |
|-------|---------------------|--------|
| Мобильное приложение -> `intelligence-devices-events-app` | OIDC через Keycloak (`auth-service-1`), токен JWT в заголовке | Короткоживущий access token, обновление refresh-токеном. Сервис проверяет подпись (по JWKS), издателя, адресата (audience) и срок |
| `intelligence-devices-events-app` -> платформа партнёра | OAuth 2.0 Client Credentials | Отдельный клиент для нашего сервиса, минимальные scope (чтение устройств, команды, управление идентификаторами), короткоживущие токены, секрет в хранилище секретов. |
| Платформа партнёра -> `intelligence-devices-events-app` (колбэки) | Подпись запроса (HMAC-SHA256 над телом и меткой времени) поверх TLS | Заголовки с подписью и временем, с установленным окном допустимого времени, идентификатор события для идемпотентности, ключ подписи отдельный на каждое окружение. |
| `intelligence-devices-events-app` -> CRM | OAuth 2.0 Client Credentials (сервисный аккаунт Keycloak) | Права только на чтение связи «собственник -> объект -> ЖК» |

#### 2.2. Авторизация
Модель: RBAC (роль «собственник») на грубом уровне и ABAC на уровне ресурса. Правило выполняется на
каждом запросе, по умолчанию доступ запрещён.

Атрибуты решения: идентификатор пользователя, объект недвижимости, ЖК, устройство, действие.

| Действие | Условие разрешения |
|----------|--------------------|
| Просмотр списка устройств | Пользователь является собственником недвижимости в ЖК, устройства показываются только этого ЖК |
| Ручное открытие или закрытие | Устройство принадлежит ЖК, где у пользователя есть недвижимость |
| Загрузка биометрии | Есть действующее согласие (актуальная версия) и устройство принадлежит ЖК пользователя |
| Добавление номера автомобиля | Устройство принадлежит ЖК пользователя |
| Удаление и отзыв биометрии и номеров | Данные принадлежат этому пользователю |
| Просмотр истории | Только события, привязанные к этому пользователю |

Дополнительное правило - связь собственника с ЖК проверяется через ответ от CRM. В JWT список ЖК не
кладётся, иначе после смены собственника токен продолжит давать доступ. Допустим кэш с коротким TTL,
сбрасываемый событием о смене собственника.

### 3. Организация взаимодействия
#### 3.1. Потоки
| Поток | Шаги |
|-------|------|
| Список устройств | Приложение -> `intelligence-devices-events-app`: проверка авторизации -> запрос связи в CRM -> запрос партнёру «доступные устройства ЖК» -> фильтрация по ЖК пользователя -> ответ приложению |
| Ручное открытие | Приложение -> `intelligence-devices-events-app`: проверка авторизации -> команда партнёру -> результат пользователю. Наш сервис записывает событие с идентификатором пользователя и идентификатором корреляции. Колбэк партнёра о том же открытии приходит без идентификатора собственника и сопоставляется по идентификатору корреляции, чтобы не было дубля в истории |
| Загрузка биометрии или номера | Согласие (версия) -> приложение -> `intelligence-devices-events-app`: проверка авторизации -> передача партнёру (фото только в памяти) -> результат. Сохраняется статус (успех или ошибка), внешний идентификатор и версия согласия. Номер сохраняется у нас для отображения |
| Колбэки событий | Партнёр -> Firewall -> `intelligence-devices-events-app`: проверка подписи, времени, идемпотентности -> быстрая запись и ответ 200 -> асинхронная обработка в `intelligence-devices-events-worker` -> история. Событие без идентификатора собственника (ручное) в истории пользователя не показывается |
| Отзыв и смена собственника | Событие из CRM -> `intelligence-devices-events-app` -> удаление биометрии и номеров у партнёра по API -> подтверждение -> статус «удалено». При ошибке ретраи, расхождения попадают в мониторинг |

#### 3.2. Решения и отказоустойчивость
- Решение об открытии принимает платформа партнёра на месте по синхронизированному списку. Мы отвечаем за актуальность списка, а не за каждое открытие.
- Выдача и особенно отзыв прав имеют приоритет и отдельный статус в интерфейсе («применено», «ожидает», «ошибка»). Для остальных настроек допустима eventual consistency.
- Недоступность сервиса `intelligence-devices-events-app` не блокирует устройства. Партнёр повторяет колбэки (минимум один раз, с экспоненциальной паузой), мы обрабатываем их идемпотентно.
- Недоступность партнёра: команды получают понятную ошибку, настройки сохраняются со статусом «ожидает применения» и отправляются позже.
- Приём колбэков должен выдерживать пики нагрузки: тонкий обработчик с быстрым ответом, обработка асинхронно.

#### 3.3. Где что хранится
| Данные | Наша БД | У партнёра |
|--------|---------|------------|
| Изображение лица | Нет (только в памяти) | Шаблон лица |
| Статус биометрии, версия согласия, внешний идентификатор | Да | Да (идентификатор) |
| Номера автомобилей | Да (для отображения) | Да |
| События устройств и история | Да | Свой журнал |
| Настройки устройств | Да | Применённые настройки для автоматических действий |
